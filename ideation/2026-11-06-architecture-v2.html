Keep what the AI cannot see at hand, and give the AI a record of who trusted it

An AI with thin trust is handed only a narrow, short-lived key. Out-of-scope requests bounce back to the voucher with evidence. Anything merely suspicious is only reported.

Overview — the three places

Untrusted (PC) Out of the AI's reach (hand side) Anyone can verify (0G) External (World / ENS / API)

Flow 1 — vouching (human → AI)

When World ID is presented with the action "vouch", it becomes a fixed pseudonym inside the app. The real name goes to nobody. Pseudonyms are exchanged when people meet, and a record of that meeting stays on the hand side.

Flow 2 — use (normal path), and one trail

The five records born from a single use are linked by the same request hash. That is exactly what is submitted to 0G (request ID, root hash).

Flow 3 — the line between punishing and notifying

What goes where

Hand side only

The root key and attestation (Ledger), plaintext API keys (Broker), your own connections (device)

Published on 0G

Vouches (pseudonym × AI × strength), violation evidence, the root hash of the trail. Anyone can count and verify them

Stored nowhere

Human names and faces. Only zero-knowledge proofs and pseudonyms move

Where zero-knowledge is used

Proof of personhood at the moment of use, and the voucher's pseudonym. Both reuse World ID; nothing new is built

Undecided and unverified

  • Which machine runs the Broker (outside the PC; the Ledger alone cannot carry it)
  • Mapping pseudonyms to contacts (idea: exchange by QR when you meet; an arrangement with added devices is also possible)
  • How far the scope is readable in the Ledger's EIP-712 display
  • Child token scheme: sign on the Ledger each time, or UCAN / Macaroon style attenuation
  • Whether using the World ID nullifier with a fixed action as the pseudonym holds up in IDKit / Agent Pass. The Agent Pass at the venue is a mock proof
  • The weight formula (scores for the 3 strength levels, how much a violation lowers it)
