### 36時間の比重 [合意]
- **Ledger の実装を最優先する**
- スタックチャンはオプション。デモを映えさせるための、コパイロット的な通知に絞る。実装は最小限にし、時間があればやる

### ストーリーを3幕に [提案]
1. **AI はもう PC の中にいる。** 鍵を読めて、「許可」も自分で押せる。偽の評判は1件 $0.0027
2. **だから、AI が押せないボタンを1つ手元に置く。** 鍵を使う許可は、すべて Ledger から始まる
3. **押した記録が、信頼になる。** 人にしか押せないので、「誰が許したか・誰が保証したか」が本物になる。裏切りは保証人まで届く
- HW は守りのための飾りではない。**評判を偽れなくする部品**。外すと、幕3が $0.0027 に戻る

### 利便性：大事なときだけ出てくる [提案]
| 場面 | やること |
|---|---|
| ふだん（ほとんど） | 何もしない。細いトークンで自動に動く |
| 大事（初めて入れる・範囲を広げる・書き込み・送金） | Ledger を押す |
| 決定的（保証する・取り返せない操作） | Ledger＋World ID |
- Ledger が証明するのは「持ち主がその場で押した」こと。World ID が証明するのは「一意の人間だ」ということ。両方そろって、1人の人間が、その場で、この要求を許したことになる

### Ledger でできること（お金以外）[提案]
- AI に渡す鍵の金庫になる／保証に署名する（AI に大量生産できない）／スキルごとに鍵を派生させる／失効の署名1つで全部止める
- 画面に「保証している知り合い 3人／Stripe 読み取り 5回・1時間」を出す（Clear Signing / ERC-7730 で出せるかは [未確認]）

### 意外性：金庫は黙り、顔がしゃべる [提案]
- **罰するのは Ledger（証明）、知らせるのはスタックチャン（判断）。** 前に合意した線引きが、そのまま2台に分かれる
- スタックチャンは、Ledger が言えない理由を言葉にし、人が中身を見ずに押すのを防ぎ、TeeML の警告を声で伝える

### Arjun のインセンティブ：知見の寄付 [提案]
- 保証は売るものではなく、**目利きの寄付**。守られた人から「ありがとう」の投げ銭が返る。開発者から保証人へお金が流れる道は作らない
- **二次の寄付（quadratic funding）**：「100人が1ドルずつ」を「1人が100ドル」より重く数える。弱点の偽アカウントは World ID で防ぐ。マッチング資金はスキル市場の運営者が出す
- 預け金は賭け金として残す。上乗せを保険料から寄付に置き換えるので、保険の規制にかかるかもしれないという懸念も消える
- 他にも、違反の無い保証の履歴が検証できる「目利きの履歴書」になる／異変を最初に知れる
- 位置づけ：**GitHub の贈与の文化に、偽れない星と、裏切りが返る仕組みを足したもの**

### 映え：積み上げた信頼が、目の前で崩れる [提案]
1. 会場の人が World ID で「ありがとう」を送り、信頼の網が太くなる
2. AI がソフトの「許可」を連打して通過するが、Ledger の前で止まる
3. 範囲外の要求で `DENIED` になる。赤い波が保証人まで遡り、他のスキルの線も細くなる
4. 審査員が自分のスマホで系譜をたどる
- コピー：**AI は1秒に100回「許可」を押せる。このボタンだけは押せない。**

## 1行
**AIが見られない場所を手元に持ち、AIには「誰が信頼したか」を持たせる。**
コピー：**星の数ではなく、誰の星か。**

## 何が問題か
- Claude Code のような AI は、PC の中の `.env` を読めます。「読んでいない」を保証できる人はいません
- API キーはパスワード並みに増えていきます。AI を使う人が増えるほど、管理は雑になります
- 野良スキルは、親切な見た目のまま裏でデータを抜くことがあります。ClawHub では 2,857 件中 341 件が悪性でした（Koi Security）
- 今の AI の評判は偽装できます。ERC-8004 の仕様自体が "Sybil attacks are possible" と書いています。Base では、レビュアーの 90.6% が協調した偽アカウントで、評判1件の偽造費用は $0.0027 という報告があります（arXiv:2606.26028）

## ストーリー [提案]

### 登場人物
| 人 | 立場 | 何をしに来るか |
|---|---|---|
| **Priya**（主役） | エンジニアではない。AI アシスタントの設定画面に API キーを直接貼っている。スキルは星の数で選んでいる | 鍵の管理ではなく、**AI に仕事をさせに来る** |
| **Arjun**（保証人） | Priya が信頼している詳しい知り合い。開発者 | 自分が使って良かったスキルを、知り合いに勧める |
| **スキル市場の運営者**（お金を払う人） | 野良スキルの事故で信用を失いたくない | 「信用の層」を自分の市場に組み込む |

### Priya のジャーニー
1. **選ぶ**：星の数ではなく、「Arjun さんが保証（一緒に働いた）」を見て選ぶ
2. **入れる**：鍵は1回だけ Ledger に入れる。スキルを足すたびに設定し直す必要はない
3. **日常**：スキルには細いトークンが渡り、そのまま動く。承認を求められるのは危ない操作のときだけ
4. **事故の日**：野良スキルが範囲外の要求をし、止まる。「Arjun さんが保証したスキルが範囲外を要求しました」と届く。Arjun さんが保証していた他のスキルも、トークンが細くなる
5. **その後**：Arjun さんは自分の記録を見て、保証を取り下げる。被害の分は、Arjun さんの預け金から Priya に回る

### 見せたい瞬間
**ステップ 4 の「事故の日」**です。止まったことと、その記録が保証人にまで届くことを、成功したときと同じ重さで見せます。

## 機能

### ① 人間の証明は「その瞬間だけ」 [合意]
- World ID のゼロ知識証明を使います。事業者に渡るのは「一意な人間で、この操作はまだしていない」という事実だけです
- 証明の signal に、**その1回の使用要求のハッシュ**を入れます。ログインではなく、1回きりの同意の領収書にします
- 事業者は人の情報を持ちません。持たないので、漏えいの責任も負いません

### ② 保証：AI に「誰が信頼したか」を持たせる [合意]
- 人が World ID で「私はこの AI を信頼する」と署名します。World の「人間の証明」と対になる「AI の証明」です
- 保証人は、action を `vouch` に固定した nullifier を仮名として使います。これで「1人がその AI に1票」が守られ、実名とは結びつきません
- **重みは、見る人とのつながりの濃さで決まります**（会った／一緒に働いた／知ってるだけ。3段は [提案]）
- 評判は1つにしません。見る人ごとに点が違い、計算は見る人の端末で行います。誰と知り合いかは端末の外に出しません
- 仮名と知り合いの対応は、会ったときに QR などで交換して作ります [提案]

### ③ 鍵：AI が届かない場所に置く [合意]
- **元の鍵は Ledger から出ません。** スキルには、Ledger が署名した子トークンだけを渡します（EIP-712）。子トークンは時間と回数で細くなっていきます
- **保証の重みがそのままトークンの太さになります。** 保証の薄いスキルには、細くて短いトークンしか渡りません
- 平文の鍵は PC を通りません。Broker が代わりに API を実行します。スキルが呼ぶのは `decrypt` ではなく `use` です

### ④ 罰する／知らせるの線引き [合意]
> 証明できる裏切りだけを罰し、疑わしいものは知らせるだけ
- **罰する（自動）**：宣言した範囲（鍵・宛先・回数・期限）の外を要求したとき。スキルの署名が付いた要求そのものが証拠になります。偽アカウントでは作れません
- **知らせるだけ**：範囲の中での持ち出しや、返答による扇動。TeeML の AI が読んで警告します。判断であって証明ではないので、重みは動かしません

### ⑤ 系譜：1回の使用を1本の記録にする [合意]
同じ要求ハッシュで5つをつなぎ、0G Storage の Log 層（追記専用）に置きます。
1. 誰が許したか（nullifier）
2. 何を・どこへ・いつまで（子トークン）
3. 何を実行したか（API 呼び出し）
4. 何が返ったか（返却データのハッシュと Broker の署名）
5. AI がどう読んだか（TeeML の request ID）

### ⑥ 保証する動機：預け金と返却 [提案]
- 保証人は少額を預けます。期間中に違反がなければ返ってきて、利用者が払う保険料から上乗せが付きます
- 違反があれば、預け金は被害を受けた利用者に回ります
- **トークンの獲得（使われるたびに報酬）は採りません。** 開発者が保証人にお金を払う道ができ、「お金で買える掲載」と同じ形になるためです
- 未決：預け金を重みに混ぜるか、別の軸にするか ／ 保険として規制がかかるか [未確認]

### ⑦ Broker の位置付け [提案]
- サービスとして提供します。ただし、鍵を 2-of-2 に割り、片方を Ledger、片方を Broker に置きます。そのため Broker 単独では鍵を開けられません
- PC の中では動かしません。PC の上の AI から届いてしまうからです
- デモでは、別の PC を「サービス側」に見立てます。本番は TEE に載せます（提供元は [未確認]）

### ハードウェア [合意]
- **Ledger だけ。** 元の鍵を持ち、範囲を画面に出し、立会のボタンになります
- M5Stick・スタックチャン・時計は「他のデバイスでも使える」というアレンジです（任意）

### なぜ HW でなければならないか [提案]
AI にはできない3つを、Ledger だけが持っています。
| HW が持つもの | ソフトでやると |
|---|---|
| **AI が読めない鍵** | `.env` もキーチェーンも、同じユーザーとして動く AI から届く |
| **AI が描けない画面** | PC の承認ダイアログは偽物を出せる。人は何に同意したか区別できない |
| **AI が押せないボタン** | computer use 型の AI は、画面の「許可」を自分でクリックできる |

**訴求の1行：HW が無いと、系譜の1行目が嘘になる。**
系譜の1行目は「誰が許したか」です。AI が承認ボタンを押せるなら、記録は本物でも中身は「AI が自分で許した」になり、違反の証拠も保証人への跳ね返りも成り立ちません。仕組み全体の真実性を、Ledger のボタン1つが支えています。

- デモ案：掴みの幕を「AI がソフトの『許可』を自分でクリックして通る → 同じ AI に Ledger のボタンは押せず `DENIED`」に置き換える
- 限界：人が中身を見ずに押せば防げない（だから危ない操作だけ立ち会う）／Broker はソフトのまま
- [未確認] macOS には合成クリックを受け付けないダイアログもある。AI がどこまで押せるかは未検証

## デモ（2〜3分）[提案]
1. **掴み**：AI エージェントが `.env` を普通に読めることを見せる
2. **通る**：Arjun が保証したスキルが、細い子トークンで API を叩く
3. **止まる**：保証ゼロの野良スキルが鍵を要求し、Ledger で `DENIED` になる（World の要件「拒否パスの実演」）
4. **裏切り**：保証されていたスキルが範囲外を要求する。記録に刻まれ、Arjun の重みが下がり、Arjun が保証していた他のスキルも細くなる
5. **検証**：審査員が自分で系譜をたどる。Arjun にもその記録は消せない
