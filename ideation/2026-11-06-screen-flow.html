Screen transitions and processes — there are only two moments we ask a person

“Press” (the device in your hand), asked every time a key is used, and “vouch” (World), asked once. These two mean different things, so they never sit on the same screen. This document exists to fix the number of screens, the transitions, and what remains.

2026-11-06kouWritten against the implementation (only what runs is written as “runs”)

Executive summary

  1. We ask a person in two situations only. “Press” = every time, on the device in your hand, whether to permit it now. “Vouch” = once, through World, who you are. We never ask twice for one and the same act. Ask twice, and we can no longer explain why it is twice.
  2. Five screens. We do not add more. No new screen is created for being stopped (it becomes a state of the same screen, and is kept in the trail). So that a judge's 90 seconds are not spent getting lost.
  3. Three things we need decided (§06). Where the path to lighting a flame starts / what leads the World waiting screen / the stand-in for days the physical device will not connect.

06What we need decided (three things)

Each can be answered in one line. My recommendation is written first.

Q1 Where does the path to lighting a flame start

  • Recommended: from both the flame screen and the trail. The motive to vouch is highest “right after finishing”. But in the demo we show only the flame screen (two paths cannot be explained in 90 seconds)
  • Alternative A: the flame screen only. Lighter to implement. But it misses the heat of “just after using it”
  • Alternative B: prompt every time a use goes through. Not taken. Asking every time mixes its meaning with pressing (on the device)

Q2 Does the World waiting screen lead with the code or the QR

  • Recommended: code first, QR secondary. Whether verification_uri_complete comes back is still [unverified]. If it does not, a single QR cannot complete the flow, so we keep a form that does not break either way
  • Alternative: QR first. Swap to it once we confirm it comes back (5 minutes to settle at the venue)

Q3 Do we keep an on-screen stand-in for days the physical device will not connect

  • Recommended: keep it. But write “stand-in for the physical device” on the screen. Never quietly pass the stand-in off as the real thing
  • Alternative: do not keep it. If the physical device dies, the demo stops. Not taken (do not add decisions on the day of filming)

07What we have not verified yet

  • World client registration (WORLD_CLIENT_ID / SECRET) is not done. Device flow has not been run end to end
  • Whether verification_uri_complete comes back (Q2 hangs on it) / the claim name of the sector identifier (we currently treat sub as the pseudonym)
  • Submission to 0G Storage is awaiting gas. The root hash comes out, but there is no tx yet
  • The custom app on the physical device and the gate are not yet joined on one screen (the 4-line values come from the same function)
